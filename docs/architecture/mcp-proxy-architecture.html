👻 GhostHands — the stdio MCP proxy monitor / control plane

Today: N agents drive one shared cua-driver daemon over MCP, with no central visibility. The proxy (shim) inserts a transparent JSON-RPC passthrough between each agent and the daemon — so every action can be seen, attributed, and optionally gated — with zero daemon changes.

2 · Inside one shim — what the proxy actually does

Four pipes + one tee. The agent half and daemon half are byte-identical streams; the shim only copies them aside (and, if armed, pauses on a matched call).

stdin ▶ requests
stdout ◀ responses

◀ read child stdout frame

3 · One tools/call flowing through — the App Store Connect Submit

  1. Agent decides to click Submit, emits {"method":"tools/call","name":"click","params":{pid:13050,element_index:60}} to the shim's stdin.
  2. tee → shim parses, stamps agent=a4059…, app=App Store Connect, appends to the bus. UI lights up instantly.
  3. gate (if armed): method=click on label “Submit” ∈ destructive → hold, push an approval card to the UI, block until you click Allow.
  4. Shim writes the frame verbatim to the child cua-driver mcp stdin.
  5. Daemon performs AXPress on the real Brave window — no cursor, no focus steal.
  6. Daemon returns {"result":"✅ Performed AXPress on [60] Submit"} up the child's stdout.
  7. tee → shim logs the result + latency to the bus.
  8. Shim writes the result verbatim to the agent's stdout. Agent never knew it was watched.

4 · What each layer can answer

WHO — process prober (works even without the shim). pgrep → parent argv → claude session + project.
WHAT + LIVE — the shim. Every click/type/launch with its pid+window, in real time.
window → agent binding — the shim sees pid 13050 in the call, so it knows which agent drives App Store Connect.
SAFETY — only the shim sits in the action path, so it's the only place to pause a destructive call or pull the kill switch.
